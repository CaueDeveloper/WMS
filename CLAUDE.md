# CLAUDE.md — Projeto WMS (Café do Sítio)

> Este arquivo orienta o Claude Code neste repositório. A fonte única de verdade de requisitos é [docs/PRD.md](docs/PRD.md); veja também [docs/escopo.md](docs/escopo.md). Em caso de conflito, o PRD prevalece.

## Visão Geral

Sistema de controle de estoque por lote para a transição entre Produção e Logística da Café do Sítio. Camada de controle intermediária (entrada, armazenagem com mapa visual, separação por romaneio) — **não substitui o SAP B1**, que segue como fonte única de saldo.

## Stack

- **Backend:** Python / Django (`wms/` = projeto, `apps/` = aplicativos: `core`, `estoque`, `recebimento`)
- **Banco:** SQLite3 em desenvolvimento, MySQL em produção — troca ocorre apenas no bloco `DATABASES` de `wms/settings.py`
- **Frontend:** Views Django tradicionais, HTML5 + CSS3 puro (sem SPA). Layout otimizado para o pior caso: coletor Zebra MC2700 (4", 800×480)
- **Impressão:** Zebra ZT421 via ZPL bruto, socket TCP/IP porta `9100`
- **Notificação:** Z-API (WhatsApp Business API) via HTTP (`urllib`, sem dependências externas), thread daemon fire-and-forget — mesmo padrão de resiliência da impressão
- **Coleta:** Zebra DataWedge em modo emulação de teclado (o scanner dispara `Enter` automático — os formulários devem oferecer bipagem contínua com `autofocus`)
- **Auth:** Django Auth nativo com `auth.Group` (`Administradores`, `Gestores`, `Operadores`) e `@permission_required`/mixins

## Regras de Negócio Invioláveis `[INVARIANTE]`

- O WMS nunca altera saldo do SAP B1 diretamente; sempre via requisições estruturadas (Outbox).
- O mapa de put-away só aparece para o operador após a transferência de saldo Produção→Logística estar processada no SAP B1.
- Endereço tem capacidade rígida de **21 paletes**. A validação de ocupação deve usar `.select_for_update()` para blindar contra condição de corrida — nunca confiar em check-then-save sem lock.
- Encerramento de guarda exige reautenticação por senha do Gestor.

## Fluxo Real do Palete (revisado pelo usuário em 2026-08-05)

A máquina de estados real do `Palete` é:

1. **Colaborador envia os dados** (Produto/SKU, Lote — digitado manualmente) em `/recebimento/receber/` (`apps/recebimento/views.py::receber_palete`). O peso não é digitado: é fixo em `PESO_FIXO_RECEBIMENTO_KG` (500 kg), aplicado automaticamente pelo backend. Não há validação de peso nem qualquer outro bloqueio — o objetivo do projeto é nunca ter paletes divergentes, então o palete sempre fica `CRIADO` e a etiqueta é impressa **imediatamente** (`disparar_impressao_async`, sem aprovação prévia do Gestor).
2. **Gestor bipa o palete impresso** em `/recebimento/transferencia/` (`apps/recebimento/views.py::transferencia_gestor`, protegida por `group_required('Gestores')`), usando o coletor Zebra: cada bipagem move `CRIADO` → `EM_TRANSFERENCIA` e o palete entra numa fila organizada por `lote` (mesma tela).
3. **Gestor aprova todos os lotes pendentes de uma vez, num único clique** (`apps/recebimento/views.py::transferencia_gestor`, marcador `aprovar_pendentes` no POST): `apps/recebimento/services.py::aprovar_lotes_pendentes` reconsulta a fila `EM_TRANSFERENCIA` a cada chamada e aprova cada `lote` individualmente via `aprovar_lote` (transação própria + `.select_for_update()` por lote — não há uma transação única para o lote em lote, de propósito: um lote esvaziado por corrida concorrente é pulado e reportado como erro, sem desfazer os demais lotes aprovados na mesma ação). Todos os paletes aprovados na chamada são promovidos para `CONFERIDO` e cobertos por **uma única** notificação combinada via `apps/recebimento/whatsapp.py::disparar_notificacao_async`/`montar_mensagem_lotes`, ao Gestor de Logística (Z-API/WhatsApp). **`AreaDestino` não é mais escolhida nesta etapa** — o campo `Palete.area_destino` permanece `None` até uma etapa futura (fora do escopo atual) que ainda vai designá-lo.
4. **Gestor de Logística bipa cada palete** em `/estoque/putaway/` (`apps/estoque/views.py::putaway`, sem restrição de grupo) em **duas etapas**: (a) bipa só o `barcode_palete` → sistema mostra SKU/descrição/lote/peso/área de destino; (b) só então bipa/digita o `codigo_endereco` disponível → `alocar_palete` grava `ARMAZENADO`.
5. **Gestor confirma o lote de guardas** com senha em `/armazenagem/confirmar/` (`apps/core/views.py::confirmar_armazenagem`) → `ARMAZENADO` vira `FINALIZADO` (sincronizado no SAP B1).

Ramo alternativo: a qualquer momento em que o palete estiver `ARMAZENADO`, qualquer usuário logado pode bipar seu `barcode_palete` em `/estoque/consultar/` (`apps/estoque/views.py::consultar_palete`) para trocar seu endereço (`apps/estoque/services.py::mover_palete`) ou registrar sua saída física do estoque, marcando-o `RETIRADO` (`apps/estoque/services.py::retirar_palete_do_mapa`) — um estado terminal, sem retorno automático a `CONFERIDO`.

`AreaDestino` (`apps/estoque/models.py`) é um cadastro simples (nome + ativo, gerenciável via `/admin`) representando a área física de transição para onde o lote aprovado será fisicamente enviado antes do put-away. **A atribuição de `AreaDestino` a um palete/lote foi deliberadamente removida da tela de aprovação** (`transferencia_gestor`) e adiada para uma etapa futura ainda não implementada — hoje `Palete.area_destino` permanece `None` após a aprovação, e as telas que o exibem (`putaway`, `consultar_palete`, `mapa_estoque`) já tratam esse caso com `|default:"—"`.

## Estrutura de Endereçamento

Grade fixa: Guardas `01`–`20` × Andares `A`/`B`/`C` × Lados `01`/`02` = 120 endereços, código de 5 segmentos no formato `001-LL-A-GG-01` (ex.: `001-02-A-20-01`), onde `001` (posição/depósito) e o `01` final são sempre fixos, `LL` é o lado (`01`/`02`), `A` o andar e `GG` a guarda (1–20, o antigo "corredor" renomeado). Capacidade permanece 21 paletes por endereço. `Endereco.montar_codigo(lado, andar, guarda)` (`apps/estoque/models.py`) é a fonte única desse formato, reutilizada pelo comando de seed e pelas views que montam a grade.

- Apps vivem em `apps/<nome>` e são registrados em `INSTALLED_APPS` como `apps.<nome>`; cada `AppConfig.name` deve ser o caminho completo (`apps.core`, etc.) com `label` curto (`core`, etc.).
- Todo incremento deve ser testável via `python manage.py test` antes de avançar de milestone.
